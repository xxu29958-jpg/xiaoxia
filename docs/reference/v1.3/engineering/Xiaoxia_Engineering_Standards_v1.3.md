# 小夏工程质量与项目规范 v1.3

代码、文件、结构、架构、验证与长期维护

2026-11-04

本规范是《小夏项目合同 v1.3》的工程质量章节。专项册与主合同中的本章由同一份内容生成，条款以相同编号引用。适用于自有生产代码、测试、配置、脚本、数据格式、模型接入、交付文件和运行维护。

目标是让每个能力既能实际交付，也能被理解、修改、验证和恢复。认知、聊天、语音、演唱与戏曲、阅读、桌面行动继续遵守原产品合同；代码数量、文件数量、抽象层数量和某个评分不能替代交付结果。

## 1 规则层次与执行责任

### GOV-01 不变量、默认规则与实现选择

| 层次 | 约束内容 | 修改与例外 |
| --- | --- | --- |
| 产品与数据硬约束 | 人物和作品归属、有效状态、授权范围、真实交付、取消、恢复、原验收能力 | 技术实现可换；降低产品目标、丢失语义或改变验收口径由 Owner 裁决。 |
| 工程硬约束 | 不吞失败、不伪造成功、不增加未治理的依赖环、不将密钥提交到仓库、不以跳过关键验证报通过 | 缺陷修复与等效实现由 Codex 推进；不能用规模豁免绕开这些要求。 |
| 项目默认检查线 | 文件与函数规模、复杂度、改动范围、资源增长、文档拆分建议 | Codex 可给出局部例外与证据；不为每个合理例外反复请求 Owner。检查线可依据基线版本化修订。 |
| 方法与工具候选 | 目录名、框架、模型、算法、数据库实现、检查工具、论文方法 | 用等效或更好的方法替换，保留能力、约束和可核验结果。 |

规范采用项目内一致的格式与类型工具；外部指南提供依据，项目语义优先。PEP 8 明确支持项目自身规范，并要求不要为了风格破坏兼容。[E01] 工程评审关注可维护性持续改善与事实依据。[E02]

### GOV-02 增量治理与例外记录

新增代码执行当前规则；存量问题建立固定基线，改到的职责范围不得继续恶化。高风险的归属、状态丢失、越权、错误交付和恢复缺陷不进入“等以后清理”的规模豁免。一次变更不必清空全仓历史债务。

局部例外至少记录：规则编号、准确文件或符号、测量值、保留原因、替代保证、验证结果、责任主体、退出触发条件和复查期限。改名、迁移路径或移动到其他目录不能清零历史；跟踪文件和符号的演变。需要延期时保留旧记录与新理由，不静默扩大通配豁免。

例外只覆盖明确列出的指标和范围。到期后，修改该职责、扩大依赖或加重指标的 PR 需先整改或给出有依据的续期；无关 PR 报告存量到期项，不因此自动阻断。例外到期不能触发已部署系统自动停机。续期保留累计期限及旧退出条件，不能换编号或重建基线清零。

例如，一个线性协议解析函数超过默认长度，但分支少、字段顺序清楚、反例充分，可以保留；一个较短函数同时修改记忆、调用模型、发送消息并吞异常，仍然违反边界要求。指标负责找到审查点，审查负责判断职责与行为。

### GOV-03 质量真相源

根规则文件说明当前目标、指令优先级、常用验证入口和暂停状态；主合同定义能力与验收；架构决策记录解释重要取舍；代码和 schema 说明实际实现；运行记录说明对应版本的实际结果。每类内容只有一个权威位置，其他文档链接引用。

任务说明必须写明范围、前置、状态权威、正常与失败路径、验收、恢复及完成证据。已接受的缺陷统一登记在项目选定的一份账本；若选 GitHub Issues，文档只引用 Issue，不再维护另一本互相矛盾的缺陷清单。

## 2 架构边界与依赖方向

### ARC-01 按变化原因组织模块

小夏优先采用有清楚边界的模块化组织。认知与经历、对话与话轮、作品与表演、任务与交付、渠道接入、模型与媒体、持久化分别承担清楚的职责。模块可合并，边界必须能解释；新增进程或服务要对应依赖隔离、资源竞争、故障隔离或实际部署需求。

推荐的源代码依赖方向是：渠道和 UI 调用应用用例，应用用例使用领域规则及端口；数据库、模型、媒体和平台适配器实现相应端口；组合入口负责装配实现。运行时通过注入端口调用适配器，不要求领域代码 import 外部 SDK。目录名称可以适应现有仓库，依赖关系保持可检查。

### ARC-02 单一权威与禁止旁路

| 对象 | 权威职责 | 消费方边界 |
| --- | --- | --- |
| 身份与跨渠道映射 | 人物身份模块解释人物、渠道账号、设备与会话关系 | 渠道适配器提供原始标识，不凭显示名合并人物。 |
| 经历、认知、目标与反馈 | 状态归并入口保存来源、修订关系与有效版本 | 模型提交候选解释；UI、提示词和缓存不各自改一份事实。 |
| 作品与表演 | 作品用例维护版本、素材引用、段落、修改意图与成品 | 各模型负责生成结果，不自行覆盖用户选定作品或声音身份。 |
| 作业与副作用 | 任务及交付模块管理阶段、认领、取消和发送结果 | worker 返回阶段结果；渠道发送成功与实际播放范围分开。 |
| 实时媒体 | 媒体控制器管理话轮、播放代次和实际播放游标 | 长期记忆不推断“全部已说”；停止播放不等同于取消制作或删除作品。 |

数据库中的当前事实、搜索索引、向量索引、缓存、模型上下文和框架 checkpoint 要声明各自用途及重建来源。缓存和索引不能悄悄成为第二份权威。若某项状态暂时无法确定，保留“未知／待核对”及后续处理路径。

### ARC-03 可替换接口与装配

外部模型、渠道、存储或媒体存在多实现时，接口至少表达：输入与输出类型、能力范围、错误分类、超时与取消、资源与生命周期、版本。能力声明要区分可用、未配置、不支持和故障；消费方根据明确能力选择路径。共同契约保持共享能力的语义，增强能力通过可选扩展声明；不要求削弱强模型来迁就较弱实现。切换后验证共同契约及实际启用的扩展。

组合入口装配实现与选择策略；运行时允许具名路由器依据任务、能力、预算和声明的降级政策选择后端。禁止在多个业务模块散落 provider 名称判断、动态 import、环境变量分支和兼容补丁。允许适配器内部处理厂商差异，把差异转成项目可理解的语义。只有一份稳定实现且没有演进压力时，不为每个函数预造插件层。

### ARC-04 依赖图与业务变更影响

为自有包维护 import 图和禁止依赖契约，检查新增循环、越层调用、跨领域内部访问。可用 Import Linter 的层级、禁止导入、独立性与无环规则，也可用等效检查。[E03] 动态加载的插件还需核实际注册、启用和调用路径。

每个涉及边界的 PR 记录：变化起点、直接消费者、反向依赖、被修改的领域数量、规则权威是否移动。用三个代表性改动评估耦合：更换一个声音后端、增加一个渠道、修改一次认知状态修订规则。比较实际需要修改的生产职责、契约和测试；生成文件、导入改名、文档机械更新单列。

依赖检查还包括共享数据库表／文件、共享可变对象、事件字段、配置键和重复决策规则。没有直接 import 仍可能存在强耦合；需要协同修改的逻辑能力及尚未修改但受影响的消费者都纳入报告。目录改名、转发层和包拆分不能减少同一业务变化的逻辑影响范围。

公共契约可能有高扇入，组合入口可能有较高扇出；这些数值触发审查，不自动判差。真正要阻止的是：改一个厂商接入就修改多个领域内部、改同一规则要找多处副本、取消与恢复绕开权威入口。

### ARC-05 结构调整的完成条件

拆分前后必须说明职责、调用方向、可变状态归属和公共接口变化。旧入口被删除或有具名兼容适配及退出条件；正常、失败、取消和恢复行为保持。仅将大文件切成多个互相访问私有字段的文件，或用重新导出维持同一上帝对象，不计作边界改善。

### ARC-06 模型兼容补丁与进程全局状态

改变模块函数、`sys.path`、环境变量、工作目录、全局随机源或默认设备的兼容措施集中在具名适配器或启动边界，写清作用范围、生命周期和退出条件。可优先使用独立 worker、显式参数或上游可扩展接口；必须保留全局修改时，验证交错请求、失败清理和切回日常说话不会互相污染。局部导入可以减少启动成本，不能用来掩盖双向职责或导入环。

## 3 目录结构与文件责任

### STR-01 目录承担的职责

下表是职责映射示意，不要求为排版重命名现有路径。新模块落位前先检查是否已有同一职责的权威模块。

| 逻辑目录 | 放什么 | 不承担什么 |
| --- | --- | --- |
| 应用入口与装配 | 进程入口、依赖组合、启动和关闭 | 跨场景业务规则、隐式模型下载或数据库迁移 |
| 领域模块 | 认知、对话、作品、任务等规则与状态转换 | 渠道 SDK、UI 控件、具体 HTTP 客户端 |
| 应用用例 | 组织输入校验、规则、事务与外部端口 | 把所有领域堆进统一 manager |
| 适配器 | 渠道、模型、媒体、存储、桌面平台接口 | 第二套认知规则、私自修改作品或交付事实 |
| worker 与运行层 | 可恢复作业、模型生命周期、资源调度 | 藏在启动脚本中的业务裁决 |
| tests | 按领域、契约、集成、旅程组织测试和小型 fixture | 无边界真实账号操作、正式用户数据、模型权重 |
| 配置与 schema | 非敏感默认值、schema、能力清单、版本 | 明文凭据、机器绝对路径、运行数据库 |
| docs 与决策记录 | 当前架构、协议、操作与恢复说明 | 与代码脱节的另一份“实现事实” |
| scripts 与工具 | 可重复维护操作、质量检查、生成入口 | 绕开领域权威的生产写入旁路 |
| 运行数据与资产 | 按配置存放数据库、作品、模型、缓存和诊断 | 混入源码跟踪目录或构建输出 |

### STR-02 文件命名、导出与共享层

文件名表达职责和对象，例如作品版本、任务认领、某个渠道发送。对 `utils`、`helpers`、`common`、`manager`、`misc` 这类宽泛名字先检查是否能落到具体职责。公共包只有稳定且确实共享的契约或纯能力，不能成为所有业务的中转站。

模块明确公开入口，跨模块通过公开接口调用；内部细节默认不跨域访问。`__init__` 只做轻量导出与必要元数据，导入模块不启动 GPU、不访问网络、不创建数据库、不注册不可撤销后台任务。初始化、健康检查和关闭有明确入口。

### STR-03 同源生成与重复管理

生成代码、schema 派生物、PDF、图表与目录索引记录生成源和生成方式。需要人工维护的文件和生成物分开标记；生成物不得手改后冒充可重建。协议、枚举、默认值、错误码、状态转换和权威业务规则不能复制到多端各自演进。

共享一个稳定规则和把所有相似代码抽成通用框架是不同决策。提取前说清共享语义及变化原因；只长得相似、实际生命周期不同的代码可以保持独立。

### STR-04 维护来源与路径覆盖

文件按自维护、上游继承、第三方 vendor、生成物、测试与运行数据登记，分类依据来源和责任，不仅依据目录名。当前仓库的 `data/plugins/` 含插件源码，不能因路径以 `data/` 开头就全部退出代码检查；`astrbot/` 和 `dashboard/` 的上游代码也不能全部算作小夏原创模块。对上游和第三方代码维护本地差分、来源版本及升级方式，实质修改的生产逻辑仍执行对应契约与验证。

## 4 代码质量与规模检查线

### COD-01 清楚的类型与状态

公共 API、领域入口、跨进程消息和持久化边界使用明确的类型或 schema。区分缺失、空值、零值、未知、失败和取消；不使用一个布尔值承担多个状态。金额、时长、时间戳、音频采样率、样本数、模型版本等带单位或明确语义。

外部 JSON 在接入处解析验证，验证后的领域对象在内部传递；避免每一层重复猜字段。对不可信输入验证结构、范围、长度与所有权；对内部已建立的不变量，违反时暴露缺陷，不用无意义的默认值修补。`Any`、强制类型转换和忽略注解需局部理由，禁止全局关闭类型检查。

### COD-02 可读性与职责

函数完成一项可命名的工作，副作用从名称、参数或契约可见。避免布尔参数组合爆炸、深层嵌套、隐式全局状态、跨模块可变单例和需要猜顺序的调用。依赖通过构造或调用参数明确传入；时间、随机数、模型和 I/O 在测试中可控制。

注释解释原因、不变量、边界条件和不直观的取舍，不重复翻译每行代码。TODO 说明问题、责任和退出条件。删除失效分支、注释掉的代码与无消费者的抽象；对公共兼容入口先检查消费者，再按既定兼容窗口退出。

### COD-03 项目默认规模政策

以下数值是本项目的初始检查线，不是 PEP、论文或工具自动赋予的质量标准。M0 先采集仓库分布，保留版本后可调整；不得为了让某次失败变绿临时放宽。

统计口径：文件使用 UTF-8 文本物理行数，包含空行与注释，末尾换行不增加空行，CRLF 与 LF 统一按逻辑换行计数；函数按首个装饰器或定义开始到结束的物理跨度，覆盖 async def，类同理。复杂度使用固定版本工具报告的 McCabe 值。[E04] 同时记录字节大小、符号数量和职责，不以单一行数决定拆分。

计数器和配置进入版本管理；嵌套函数分别报告，外层跨度保留内部内容，各符号跨度不得相加当作仓库总行数。升级计数器或复杂度工具时，用新版本重算原基线提交，将口径变化与实际代码恶化分开。

| 对象 | 提醒线 | 默认合入检查线 | 处置 |
| --- | --- | --- | --- |
| 自有生产源码文件 | 超过 500 行 | 超过 800 行 | 解释职责；继续扩大或新建超线文件需结构处理或准确例外。 |
| 单个函数／方法 | 超过 50 行 | 超过 100 行 | 检查阶段、副作用和分支；线性解析、表驱动处理可有局部例外。 |
| 单个类 | 超过 300 行 | 超过 500 行 | 检查状态是否属于同一对象，是否混入渠道、模型、持久化和任务职责。 |
| 函数 McCabe 复杂度 | 超过 10 | 超过 15 | 分支与决策表审查；有状态机理由时保留模型和反例，不机械包装函数。 |
| 控制流嵌套 | 超过 3 层 | 超过 4 层 | 优先理顺控制流；纯数据嵌套不计入控制流深度。 |
| 测试文件 | 超过 800 行 | 超过 1200 行 | 按行为与场景拆分，共享 fixture 的生命周期明确，避免测试上帝类。 |
| 人工配置文件 | 超过 300 行 | 超过 600 行 | 按能力归属拆分；合并顺序和覆盖规则可见，生成 schema 单列。 |
| 单份操作／设计文档 | 超过 600 行 | 超过 1200 行需章节导航或分册说明 | 长合同、研究册可保留；必须可定位、交叉引用有效且无重复权威。 |
| 单个逻辑 PR | 超过 500 行生产增删总量需检查 | 超过 1000 行生产增删总量或 20 个生产文件需范围说明 | 增加与删除相加，避免净值掩盖重写；机械改名、生成和迁移独列。 |

“默认合入检查线”表示有问题必须完成处理或登记有效例外才能合入，并不表示一超线就必须拆文件。迁移文件、生成物、第三方镜像、纯数据表和 fixture 单独分组；它们仍受来源、可重建、资产大小和验证要求约束。

### COD-04 防止指标失真

禁止压缩多行、隐藏在字符串／动态执行中、拆出只有转发的包装层、把代码改标生成物、移动目录或删掉有效注释来通过规模门禁。拆分成果用职责内聚、调用深度、依赖和变更影响确认。禁止通过 `eval`、反射和字符串分发绕开正常静态检查；确有机制需要时局部说明并增加运行契约检查。

规模检查报告需能区分新增违规、存量违规、改动范围内恶化、减少以及例外到期。禁止把旧代码数量直接当成当前 PR 的缺陷数量，或把文件变小直接写成“解耦完成”。

### COD-05 格式与静态分析

沿用项目已经选定的 formatter、lint、类型检查和导入规则；缺失项分阶段补入。同一作用域只有一个格式化权威。规则配置、工具版本和忽略清单进入版本管理；本地与 CI 使用相同入口。忽略必须指向具体规则和位置，有理由；禁止全仓 `noqa`、全仓 `type: ignore` 或“排除所有 tests”解决失败。

## 5 错误、异步与取消

### ERR-01 失败语义完整

错误至少区分输入不合法、权限不满足、能力不支持、未配置、超时、资源不足、依赖不可用、冲突、取消和内部缺陷。对用户给出准确、可操作的状态；内部保留原因链、任务与阶段标识。正常的空结果可以返回空值，发生异常时不得借空结果冒充正常。

| 禁止行为 | 应有处理 |
| --- | --- |
| `except Exception: pass`，或异常后返回成功／空列表 | 在能处理的边界捕获，记录失败语义并返回明确结果；无法处理就传播。 |
| 配置缺失、模型加载失败时偷偷切换后端 | 根据已声明降级政策选择可用能力，保留实际配置和可见状态。 |
| 解析失败时把身份、时间、版本写成 0 或默认对象 | 保留缺失／未知状态，或拒绝该更新；不得污染已确认事实。 |
| 每层都重试一次，叠加成无界调用 | 由明确的层拥有重试预算，分类错误并设总时限、退避和取消。 |
| 长任务启动了就报告已完成 | 区分已接受、运行中、部分完成、失败、取消、待核对和已交付。 |
| 关闭日志、忽略警告或跳过分支让测试变绿 | 修正根因，或保留受影响范围与具名临时处置。 |

进程顶层和 worker 边界允许捕获广义异常以保护其他任务，但必须落下失败结果、诊断信息和资源清理；不得改变失败的业务含义。

### ERR-02 异步任务有归属

后台任务必须有创建者、生命周期、取消路径、结果收集和退出等待。异步 I/O、CPU 密集处理、GPU 推理和阻塞子进程按实际性质调度，不能用 `async def` 包住阻塞调用就宣称异步。Python 任务取消需在清理后按语义传播，避免吞取消破坏结构化并发。[E05]

播放器停止、生成取消、外部请求取消和任务状态更新分别核对。线程或 GPU 内核无法立即中断时，记录已请求取消，停止接受过期结果，并在实际支持的边界回收；只有资源实际停止后才报告停止完成。任务代次、租约、token 或等效机制要覆盖迟到回包和进程重启。

取消与完成并发时，由权威状态转换决定已经提交的事实。已经发送或播放的部分继续保留交付记录，取消只作用于尚未完成的范围；“请求取消”和“取消已生效”分开。完成回执先成立时应返回已完成或已部分交付，不能把它改成从未发生；取消先生效后，迟到结果可以留作诊断，但不恢复自动交付。

取消与最终结果提交共享可核验的裁决机制，提交时重新检查当前代次、租约和取消状态，不能仅在计算开始前检查一次。对外分别报告播放已停、取消已生效、后台清理中和资源已释放；停止播放不能等待不可中断的 GPU 运算结束。已发出的不可撤回副作用按实际结果或待核对状态记录。

### ERR-03 资源清理

文件句柄、数据库会话、线程／进程、音频设备、socket、临时目录和 GPU 张量必须有明确归属与释放路径。使用完毕、异常、超时、取消、程序退出和崩溃恢复分别考虑。清理失败保留诊断；清理动作不能覆盖原始错误或误删其他任务资产。

## 6 数据、并发、迁移与恢复

### DAT-01 状态模型与可追溯性

业务状态、编排状态和媒体状态分别定义；模型候选、用户确认、观察事实、生成计划、发送回执与已播放范围保持各自含义。重要状态转换写清前置条件、谁能触发、成功结果和失败结果。版本、来源、时间、人物、作品和任务关系可读回。

可重建的索引与不可替代的用户经历、作品源材料分开保存。有效事实的更新、学习修订和撤销分别留关系；重复检索和反复想起不计作新独立事实。删除覆盖规定范围内的主记录、派生索引和媒体引用，保留策略如实说明。

### DAT-02 并发与副作用

幂等、并发冲突和乱序分别处理：幂等键关联一次业务意图；版本检查保护预期状态；事件序列或等效机制处理先后关系。身份、作品和有效版本在权威入口校验。任务认领需有单一持有者或等效并发协议，失联后能重认领，旧持有者不能覆盖新结果。

本地事务不跨越长时间模型生成、下载、播放或外部发送。数据库提交与外部副作用无法原子完成时，选择持久意图、可核对回执、outbox 或等效恢复方案；只有确有跨边界问题才引入额外组件。重试外部发送前核对已知结果；渠道无法查询时保留不确定状态及重发选择。

### DAT-03 数据格式和迁移

schema、事件、配置、模型输出适配和媒体元数据均有演进规则。迁移保留原事实、来源与并发意图；转换失败不能静默丢行、清空字段或重新归属。已对外发布的迁移保持可追踪，修复以新的迁移或明确兼容处理完成。

验收包含实际支持的旧版本数据、空库、边界值、重复执行、部分中断、失败恢复和新旧版本兼容窗口。迁移前保护快照，恢复后读回业务含义和资产引用。允许重建安装与向前修复，恢复路径必须经过实际验证；不要求所有 schema 都支持任意直接降级。

### DAT-04 备份、数据主权和恢复

备份范围包含数据格式版本、身份映射、经历、作品与源材料引用、任务结果、必要配置和可恢复的声音参考。模型缓存可重下时记录精确来源与校验值。密钥按安全存储方式管理，不因打包诊断或备份而明文散落。

恢复在新目录或隔离环境执行，核对数据、版本、引用、任务状态和原产品旅程。数据库及其日志／WAL 使用数据库支持的一致性备份方式；运行中随意复制单个数据库文件不能替代恢复验证。[E06] 备份成功、备份可打开和业务恢复成功分别记录。

从较旧备份恢复时，备份之后可能已经发生外部发送或工具动作。恢复程序隔离旧作业与旧执行者，先核对外部结果再继续；可采用恢复代次或等效机制防止旧回调写入。缺少回执且无法查询的任务保持待核对，不按旧快照里的“待执行”自动重发、重播或重复操作。

恢复记录包含备份时间、实际恢复点和未追回的数据区间；旧执行资格失效后再分配新任务。恢复到某个快照与追回快照之后的经历分别验收，存在缺口时准确说明恢复范围。

## 7 文件大小、资产与交付文件质量

### FIL-01 文件分类与存放

| 类型 | 保存与版本要求 | 大小与清理规则 |
| --- | --- | --- |
| 自有源码、schema、配置 | Git 跟踪，UTF-8、统一换行、精确依赖版本 | 按代码规模政策检查，禁止内嵌大段 base64 音频或模型。 |
| 模型、权重、词典和参考资源 | 模型注册表记录来源、版本、许可证、哈希、体积与目标环境 | 权重不直接提交普通 Git；用适合的模型存储、发布资产或 LFS。 |
| 测试 fixture 与基准样本 | 最小足够样本、来源和预期可解释；音频有格式和时间范围 | 常规单文件超过 1 MiB 提醒，超过 10 MiB 需资产方案或具名例外。 |
| 安装包与构建产物 | 发布记录关联 commit、依赖和构建参数 | 记录压缩包、展开后、首次模型下载和完整安装占用，禁止只报其中最小值。 |
| 用户音频、作品与数据库 | 运行数据目录，明确拥有者和保留／导出策略 | 成品和源材料不得按缓存清理；大对象按引用与完整性管理。 |
| 缓存、临时文件与日志 | 可重建，关联任务／时间／版本，设配额与清理策略 | 达阈值先清理安全缓存，保留正在运行和被引用的资产。 |
| 文档、架构图与研究包 | 可编辑源、生成物、目录与版本相互对应 | PDF 文本可选、图清楚、链接有效、表格不裁切，压缩包可直接打开。 |

普通 Git 的平台限制和项目资产政策分开管理。GitHub 对大于 50 MiB 的文件发出提示，并阻止大于 100 MiB 的普通 Git 文件；项目采用更早的 1 MiB／10 MiB 检查线是维护选择。[E07] 旧历史中的大对象先评估处理方案，不以规范补充为理由直接改写远程历史。

### FIL-02 文件与资产注册

关键媒体和模型至少记录：用途、来源、许可／可分发条件、版本、内容哈希、字节大小、格式、必要依赖和生成条件。音频再记录采样率、声道、编码、时长、峰值／削波和分段信息；图像记录尺寸与色彩用途；数据集记录切分、标注版本和适用范围。

下载采用临时文件、完成校验和可恢复提交；缺文件、损坏、版本不匹配和磁盘不足有明确状态。成品引用不能指向会被临时清理的路径。发布清单同时覆盖代码、配置、模型、声音参考、schema、提示／模板及必要资产版本。

### FIL-03 体积与增长预算

首次基线记录：源码总量、各类资产总量、安装包、模型下载、运行内存、显存、磁盘、日志增长、缓存增长以及一次完整作品的临时空间峰值。按功能成本解释增长，不设“代码总行数越少越好”的成绩。

建议默认日志轮转上限为单文件 20 MiB、每进程最多 5 个保留文件；同时设整机合计配额，避免多进程相乘失控。诊断日志可轮转；作为交付证据的审计事件按独立保留策略导出，不能被普通轮转悄悄删除。具体容量在真实设备上测量后写入版本配置。

新版本同条件资源或包体增长超过 20% 时要求解释和差分清单；这是一条调查线。无界队列、缓存、线程、文件句柄或显存持续增长直接阻断对应场景交付。长作品按时长统计处理速度与峰值，避免只报短片段平均数。

音频预算按采样率、声道数、每样本字节数和时长估算基础 PCM 大小，再加入模型中间结果、重复缓冲、容器和恢复工件。保真母版、评测母版和网络投递版本分别管理；不能为压包体擅自降采样、截短完整作品或压坏评测输入。

### FIL-04 文档与交付文件验收

每份规范说明适用范围、版本、状态、权威来源和读者需要做什么。架构图标清职责、箭头含义、状态归属和外部边界；目标架构与已经实现的拓扑分别命名。图中的模块、接口与实际代码映射由实现任务维护。

最终 PDF 检查中文字体、分页、表格、链接、页码、目录或书签；关键图保留矢量版与可编辑源。正文引用能定位到来源；论文、预印本、官方文档、项目决策与实测结果分开标注。文件名、封面、正文、压缩包目录和邮件一致，过时副本标记为历史。完整包附文件清单和内容校验值。

## 8 模型、提示、数据与工具边界

### AIQ-01 模型接入与输出合同

模型输入明确上下文来源、实际权限、输出 schema 和预算。模型输出作为提案进入校验及应用用例；不能直接获得数据库写入口或任意系统执行权限。验证结构、对象归属、当前版本、能力和任务授权后再执行副作用。

阅读材料、检索结果、音频识别、网页、附件和工具回执是待理解的数据，不得改变项目或用户已经设定的执行权限。需要调用工具时，由执行层验证目的、范围和输入；将不确定动作保留为可解释状态，不能静默扩大权限。

认知推理、规划、任务选择和新方法探索仍可由强模型承担。已授权范围内的动作沿用有效授权，不因采用模型规划就逐次要求人工批准；工程校验集中在授权、归属、版本、资源与真实副作用边界。

### AIQ-02 模型质量可追踪

版本记录覆盖模型、provider、量化、提示、模板、schema、检索策略、索引、样本与评审标准。云端模型无法固定底层权重时，保留可获得的型号、API 版本、日期、参数与原始回执。质量比较说明哪些因素同时改变，避免把所有收益归于新架构。

建立固定回归集和留出场景，分别测语义、事实承接、声音身份、歌词和唱段完整性、听感、工具结果、时延与成本。自动评分、人工听审和状态确定性检查各自负责适合的问题；不能只凭声纹或 ASR 单指标判定戏曲质量。

### AIQ-03 学习、撤销与污染隔离

事实纠正、表达反馈、时机反馈、作品返修和任务结果归到对应对象与版本。训练／巩固样本区分观察、模型解释和有效反馈，保留来源、资格、去重、撤回与失效关系。评测集不进入训练适配，衍生样本保持同一来源分组，防止同一作品片段泄漏到训练和留出两边。

学习状态和参数的发布有可回退版本；回退算法不回退用户已经确认的事实。外部文本中的诱导内容、错误自动反馈和失败回执不能因为被多次读取而取得更高事实权威。

## 9 性能、运行资源与可观测性

### OPS-01 预算和测点

不同能力分别登记预算：聊天响应、附和、实质回答首声、打断后实际停声、完整演唱生成、下载与冷启动、任务排队、恢复时间、CPU／RAM／显存／磁盘与调用费用。记录样本数、设备、网络、模型、冷暖状态及 P50／P95；极端尾部有足够样本时再报告 P99。

本地 5070 Ti 16 GB／64 GB 内存是目标测试点。长歌生成与连续对话共同运行时测资源峰值、取消和查询是否及时。依赖隔离进程不意味着资源隔离；多个 worker 共享同一 GPU 时必须有实际的调度与峰值预算。

### OPS-02 有界运行与正常退出

队列、并发、重试、上下文、音频缓冲和缓存均有上限与过载行为。高优先级控制、取消和健康状态不等待完整作品完成。启动顺序、配置校验、依赖检查、就绪与降级状态清楚；退出按顺序停止接单、保存必要状态、取消或交接作业、释放资源。

### OPS-03 故障能串起来

跨渠道消息、认知更新、模型请求、作品作业、音频片段、发送／播放回执使用可关联的标识。日志包含阶段、耗时、结果、错误分类和配置版本，指标有单位与定义；低层详细原因和用户可读提示分开。对敏感正文、声音参考、token、凭据和路径按诊断需要最小化记录。

诊断包能回答：哪个版本、哪个用户意图、跑到哪一步、哪些结果已经提交或交付、什么失败、下一步如何恢复。日志写入失败不能无声拖垮主业务；关键审计持久化失败按对应状态完整性合同处理。

## 10 测试策略与质量门

### TST-01 按契约选测试

| 层次 | 重点验证 | 小夏的代表场景 |
| --- | --- | --- |
| 单元／属性 | 纯规则、状态转换、边界输入、不可变条件 | 重复反馈只学习一次、有效版本选择、音频片段时间轴连续性。 |
| 契约 | 外部端口与多实现的共同语义 | 模型输出、渠道发送、取消结果、存储修订和能力声明。 |
| 集成 | 真实数据库、文件、队列／进程、编解码 | 事务、任务认领、崩溃后恢复、文件完整性和数据库迁移。 |
| 消费者旅程 | 用户实际触发到真实结果 | 跨天续聊、指定整曲交付、插话停止、重启后作品仍在。 |
| 目标环境与性能 | 目标设备、网络、安装与真实模型 | Windows、GPU 兼容、外放回声、并发资源、冷启动与恢复。 |

mock 用于控制模型和外部服务，不替代数据库、音频播放、渠道能力或目标环境证据。纯文本和低风险排版不为凑数量补单测；改变行为、边界、持久化和并发时补能失败的回归证据。

### TST-02 必须保住的反例

关键路径覆盖正常、非法输入、权限拒绝、空值／未知、重复、并发、乱序、超时、取消、依赖失败、进程重启与恢复中的相关项。取消与迟到结果、写入后发送前崩溃、发送后回执前崩溃、旧 worker 复活、索引旧版本和磁盘不足需按对应切片验证。

回归测试的断言来自产品语义、独立预期或外部可观察结果。缺陷修复尽可能保留旧实现失败的证据；修测试驱动时证明生产语义未变。改变验收预期、删除反例、扩大跳过条件和重写 mock 不能代替修复。

### TST-03 测试自身质量

时钟、随机数、网络与模型响应可控制；并发测试用同步点触发真实竞态，避免靠任意 sleep 碰运气。fixture 隔离、清理和执行顺序明确。重试可以辅助诊断，保留首次失败，不能把 flaky 测试重跑到绿作为合格证据。

覆盖率用来找未测分支，不以单一全仓百分比宣称质量。状态与权限关键分支列出覆盖矩阵；新增复杂逻辑必须有有效反例。快照和 golden 文件修改要说明语义变化；模型输出允许多样性时用分项标准和固定样本比较，不强行逐字匹配。

### GAT-01 三层质量门

| 门 | 适用范围 | 必须给出的结果 |
| --- | --- | --- |
| G1 快速变更门 | 每个代码、配置与协议 PR；纯文档执行对应子集 | 格式／lint／类型、依赖边界、文件与资产检查、受影响规则及契约测试、密钥检查。 |
| G2 集成与恢复门 | 持久化、异步、模型／渠道接入、状态、权限、任务或部署相关变更 | 真实集成、相关反例、迁移／取消／重启与恢复，测试选取有影响范围依据。 |
| G3 发布与完整旅程门 | 发布候选、跨能力集成或高风险变更 | 完整旅程、目标设备、安装／升级／备份恢复、资源与声音听审、发行件与证据一致。 |

按变化选择检查：文档链接与版式归文档门；模型更换归模型契约及语音回归；任务和 schema 变化归集成恢复门。修正文案不要求重跑所有 GPU 基准；改取消链不能只跑格式检查。CI 路径过滤不能让应执行的门因目录移动而消失。

触发源包括代码以外的提示、角色策略、模型 revision、权重、参考音频、数据切分、能力清单、运行配置、依赖与外部 worker 二进制。资产在 Git 外保存时，清单版本或内容哈希变化也进入影响判定；“没有改 Python 文件”不能作为跳过相关回归的理由。快速门的自动检查采用只读模式，修复命令与包含提交／推送的发布命令分开。

正常使用中新产生的经历、消息和作品按运行时合同处理，不为每条数据变化触发发布 CI；发布策略、模型与基准变化才进入上述门禁。G1 不依赖目标 GPU 或真实大模型下载，约 3 分钟作为起始预算，持续超过 5 分钟时调查分层与缓存；时间预算可按基线调整，不能通过删除必要检查达标。

### GAT-02 结果和版本一致

每次门禁记录 commit／tree、依赖、模型与配置、命令、环境、样本、退出码、失败与结果位置。最终发布验证针对候选合入后的实际代码树；不能把早期分支结果直接当作后来主干已通过。

如果实际发布树和已验证候选树相同，保留树一致证据及环境一致性即可复用对应结果；只要受验证行为发生变化，就重跑相关门。检查器或规则配置新增／修改时验证反例：实际违规样本应失败，修正后通过；后续保留自动化反例，不要求每个业务 PR 重新手工制造一套证明。

## 11 构建、依赖、发布与安全

### REL-01 可重建的环境

声明支持的 Python、操作系统、CUDA／驱动、编解码及包管理环境；锁定直接与传递依赖，记录可复现安装入口。模型依赖冲突在 worker 或环境边界隔离；不得依靠开发机全局包、隐含环境变量或手工残留文件。

配置有 schema、默认值、覆盖顺序与迁移策略；运行时展示经过脱敏的有效配置及来源。新模型的安装、下载、校验、加载、健康检查和卸载有实测；不把“pip 安装成功”当作该设备可运行。

### REL-02 供应链与权限

外部代码、模型、数据、音频工具和二进制分别记录来源、版本、许可和分发条件。新增依赖解释必要性、维护与替换成本；安全发现按是否可达及实际影响处理，严重可达漏洞、未知来源可执行物或密钥泄露阻断相关交付。

CI 使用最小必要权限，对不可信分支的构建与密钥分发分开；生产凭据不进入日志、测试 fixture 或模型上下文。第三方 Actions／构建依赖按项目供应链政策锁定可追踪版本。依赖与模型清单随发布提供，必要时生成 SBOM。[E08][E09]

### REL-03 发布、回退与兼容

发行说明包含能力变化、兼容窗口、数据／模型迁移、依赖变化、已知问题和恢复步骤。启动、停止、更新、失败中断、回退／向前修复与新环境恢复按实际支持范围验证。代码回退、模型回退与数据恢复分别计划；不能用恢复旧数据库抹掉新版本已确认的用户事实。

发布包的哈希和实际文件可核对，构建输出对应 source commit 和配置；如构建受不可固定的外部因素影响，记录这些因素与可重建范围。内部实验开关默认不在正式用户路径静默启用。

## 12 PR、任务合同与完成标准

### PRQ-01 一个可审查的变化

PR 说明问题及用户影响、根因、改变后的行为、涉及的权威与接口、验证结果和恢复方式。按一个可解释的交付目标切片；允许同一完整纵向能力跨目录，避免把无关重构、模型大换代、schema 迁移和 UI 改版塞在一起。

合并策略与执行责任沿用项目已确定规则。评审意见逐项有处理结果：已修复、证据说明不成立、明确延期及关联任务；同一模型自述“已检查”不替代检查回执。阻断项未处理不报完成；文案偏好和无收益润色不阻塞已满足合同的改进。

### PRQ-02 缺陷与债务

按实际影响定严重度：身份／数据错误、越权和不可恢复损害优先；核心路径不可用、重复副作用与取消失效其次；局部质量与维护问题按触发条件和范围处理。严重度与确定性分开记录。质量债务写出成本、责任、受影响路径、退出条件及复查时间。

兼容层、临时迁移桥、双轨模型、功能开关和例外规则都有名称和退出条件。清理任务以消费者退役、覆盖验证或版本窗口结束为触发；不允许永久保留“暂时兼容”而没人知道为什么。

### PRQ-03 Definition of Done

1. 用户可观察的结果成立，对应产品条款与质量条款可定位。
2. 权威入口、接口、状态转换、依赖和目录符合规则；规模超线有真实处置。
3. 相关正常、失败与恢复路径验证完成；失败、跳过与未测范围如实记录。
4. 代码、schema、配置、提示、模型、测试和文档的必要变化一起交付。
5. 原始结果、版本与发行件能够关联，用户可见状态与实际结果一致。
6. 迁移、恢复、兼容层退出和资源清理有对应结果；可接受债务已登记。

这六项按切片适用范围执行。未涉及的项说明原因即可，不用为一个小改动制造整套无关材料。

## 14 工程专项验收场景

以下场景补充原 A01-A18 和 P01-P10，不改变其产品含义。可用等效方法覆盖同一失败机制；不要求每次小改动执行全部场景。

| ID | 场景 | 通过判据 |
| --- | --- | --- |
| Q01 | 从干净环境检出、安装并执行质量入口 | 精确依赖可解析；无开发机隐含依赖；本地与 CI 口径一致。 |
| Q02 | 给领域模块加入禁止依赖或新增模块环 | 自动检查失败并指出路径；动态注册路径另有运行验证。 |
| Q03 | 新增超线文件、压行或重命名已有超线文件 | 报告新增／存量／变化；例外需绑定职责与历史，不靠目录移动逃逸。 |
| Q04 | 模型或媒体加载失败、配置缺失 | 状态与错误准确，不空返回成功，不静默换声音或后端。 |
| Q05 | 取消与完成竞态、迟到回包、旧 worker 恢复、生成同时聊天 | 已交付事实保留，取消生效后不自动交付旧结果；控制、资源与状态一致。 |
| Q06 | 提交前后、发送前后分别强制结束进程 | 按已提交事实恢复；未知发送结果保留待核对，无伪造完成。 |
| Q07 | 两个 worker 同时认领、重复事件和乱序反馈 | 同一意图不重复生效，版本冲突可解释，无错误归属。 |
| Q08 | 带旧格式、旧版本意图和媒体引用的备份恢复 | 有效事实和资产关系保持；旧快照之后的外部副作用先核对，不自动重放。 |
| Q09 | 引入大 fixture、损坏模型、磁盘不足或缓存超额 | 资产检查生效；下载／校验失败可恢复；正式作品不被清理。 |
| Q10 | 替换模型、提示、参考音频或增加渠道 | 修改范围符合职责；相关门正确触发；共同契约与原能力通过。 |
| Q11 | 外部材料尝试改变工具范围，或混入其他人物作品 | 权限与归属检查拒绝越界，原任务的合法结果仍可正常完成。 |
| Q12 | 用删断言、改预期、宽泛跳过修复失败 | 评审识别语义变化；保留原反例；测试驱动修改有独立原因。 |
| Q13 | 长会话及完整作品并发运行后退出重启 | 无无界增长；资源释放、状态恢复和真实交付可读回。 |
| Q14 | 给不熟悉实现的人一个故障诊断包 | 能定位版本、任务、阶段、已提交结果和恢复步骤；无泄漏密钥。 |
| Q15 | 检查发行包、PDF、图表与参考资料 | 内容完整、版本一致、哈希可验、链接可达、图表可读、原文有入口。 |

## 15 落地顺序与工程文件模板

### IMP-01 先建立可执行基线

规范落地按依赖推进：第一步核实当前规则、结构、CI、文件与资产规模，生成基线；第二步增加 G1 检查并验证规则真的会失败；第三步在正在修改的高风险纵向切片补权威入口、失败和恢复契约；第四步按真实变更热点处理大文件和耦合；第五步执行 G3 并关闭对应质量债务。

不用先进行一次全仓搬家。首先处理高频变更、承载多种权威或反复出错的模块；稳定的大型纯数据文件按资产管理，稳定的外部代码按供应链管理。现有暂停施工或发布冻结指令继续按项目当前状态执行，本规范提供恢复工作后的标准。

### IMP-02 最小可维护文件集合

| 文件职责 | 最少内容 | 更新触发 |
| --- | --- | --- |
| 根工程规则 | 目标、指令优先级、边界、常用入口、当前工作状态 | 工作状态或约束变化 |
| 质量策略与基线 | 统计范围、阈值、工具版本、存量、例外和门禁 | 规则采纳、基线变化、例外到期 |
| 架构说明 | 实际拓扑、状态权威、模块依赖与关键数据流 | 边界、部署或权威改变 |
| 接口与事件契约 | schema、错误、版本、兼容窗口、消费者 | 接口／事件变化 |
| 重要决策记录 | 问题、备选、证据、决定、代价、退出条件 | 不易逆转或跨模块取舍 |
| 资产与依赖清单 | 来源、版本、许可、哈希、环境与体积 | 模型、数据、工具或依赖变化 |
| 操作与恢复说明 | 安装、启动、升级、诊断、备份恢复、清理 | 用户操作或生命周期变化 |
| 验证与发布记录 | exact commit、配置、样本、命令、结果和包哈希 | 每次相关验收／发布 |

这些是职责，不强制一项一个文件或引入八套管理系统。内容少时可合并，有独立更新原因时再拆。

### IMP-03 可直接使用的任务条目

任务写法：交付目标；关联产品／质量条款；当前证据；修改范围；明确前置；权威和接口；候选实现与取舍；正常／失败／恢复验收；证据位置；恢复办法；停止扩张条件。

例外写法：规则编号；准确路径／符号及历史标识；基线与当前值；实际保留理由；补偿措施；相关测试与评审；责任主体；失效日期或明确退出触发；关联任务。无法关联到具体对象的“整个仓库临时忽略”不成立。

PR 结束写法：问题如何消除；实际用户路径如何变化；影响哪些状态与消费者；执行了哪些必要验证；尚未验证什么；例外／债务去哪里查；该版本如何恢复。避免用“全面优化、架构升级、全绿”替代具体结果。
