# 小夏 v1.3｜文件地图、代码度量与快速 CI 补充合同

来源：Owner 于 2026-11-04 在当前 Goal 中提供的完整补充。与主合同共同作为当前交付约束。

本补充沿用主合同 ARC-01～06、COD-01～05、STR-01～04、TST-01～03、GAT-01～02 和 EQ1～EQ4，不建立第二套冲突的工程标准。

**总原则：度量用于发现真实工程问题，门禁用于快速阻断真实回归；不以测试数量、代码数量或文件拆分数量评价质量。**

## FM-01：建立文件影响地图

每个纳入维护范围的文件应能关联：

- 相对路径、文件类型、语言及来源分类。
- 自有生产／测试／脚本／配置／schema／上游／vendor／生成物。
- 所属领域、维护责任和主要变化原因。
- 公开接口、状态权威、直接依赖与反向消费者。
- 共享数据库表、事件、协议、配置和模型输出关系。
- 动态插件注册、实际调用入口。
- 对应测试组、风险等级、质量门和有效例外。

地图以源码、配置和实际注册关系自动采集为主；仅无法可靠推导的业务语义由人工标注。

禁止维护一份与真实代码长期脱节的手工文件清单。

## FM-02：建立完整代码规模统计

每次基线与重要 PR 至少输出：

1. Git 跟踪文件总数与总字节数。
2. 仓库全部文本文件物理行数。
3. 自有生产代码文件数、物理行数、有效代码行数。
4. 测试文件数与测试代码行数。
5. 工具、脚本、运维和构建代码行数。
6. 配置、schema、迁移文件及行数。
7. 前端、后端、认知、语音、演唱和平台适配各领域行数。
8. 上游原样代码、本地修改的上游代码及第三方 vendor 行数。
9. 生成代码、文档和不可按代码行数计量的二进制资产。
10. 各语言文件数、行数及增长差分。

物理行数、有效代码行数、注释和空行分别统计，不混用口径。

提供两个明确的汇总：

- **Repository Total**：整个仓库的实际规模。
- **First-party Production Total**：小夏自维护生产代码的实际规模。

各分类互斥，汇总能够复算，不重复计数。

## FM-03：复杂度与可维护性

保持现有 Ruff C901 标准，并增加以下报告：

- C901 超过 10、超过 15 的函数数量。
- 最大复杂度及 P50／P90／P95 分布。
- 文件、函数、类长度及超线分布。
- 嵌套深度、函数数量与职责集中情况。
- 新增违规、存量违规、改动范围内恶化和改善。
- 高复杂度且高频修改的实际热点。
- 各项有效例外、退出条件和历史变化。

复杂度不得孤立评价。

优先调查同时具有以下特征的模块：

**复杂度高＋修改频繁＋下游消费者多＋承担关键状态权威。**

禁止通过压缩代码、拆分转发包装、移动目录或改名逃避规模检查。

## FM-04：架构与耦合度统计

建立源码依赖图及业务影响图，识别：

- 新增依赖环和越层访问。
- 跨领域访问内部实现。
- 高扇入、高扇出模块。
- 重复业务规则与多头状态权威。
- 共享可变全局状态及隐式运行时补丁。
- 动态注册关系与静态导入图不一致。
- 修改某条规则时需要协同修改的生产职责数量。

针对以下三个代表性改动持续测量实际影响：

1. 替换一个语音模型。
2. 新增一个聊天渠道。
3. 修改一次认知状态修订规则。

以真实消费者与必要修改范围判断耦合是否改善，不以目录数量或文件变小宣称解耦。

## FM-05：增量度量与趋势

每个 PR 提供相对于明确基线的差分：

- 新增、删除和净变化代码行数。
- 各类别代码规模变化。
- 新增、移除及改动文件数量。
- 复杂度新增与减少。
- 依赖环、跨域耦合和消费者变化。
- 新增公共接口、协议与状态权威变化。
- 测试执行数量、耗时及实际失败机制。
- 有效质量例外及其变化。

历史改名、目录移动、格式化和机械生成单独归类。

报告必须同时保留绝对总量与变化量，不能只展示对自己有利的净减少结果。

## FM-06：由文件地图驱动云端 CI

变更进入 CI 后：

**Git Diff → 文件影响地图 → 消费者与风险分析 → 最小充分测试集合 → 检查结果与覆盖说明**

G1 优先快速反馈；G2 根据状态、迁移、并发和恢复风险选择相关集成测试；G3 面向发布候选执行完整旅程。

不得因某个改动文件不在测试目录就跳过其真实消费者。

无法确定影响范围时，报告地图缺口并执行必要的扩展检查，禁止静默通过。

不强制每个 PR 重跑所有历史测试，也不允许为了追求速度删除有效的关键反例。

## FM-07：门禁自身也要接受验证

选取真实且可控的反例，验证：

- 超过 C901 检查线能被识别。
- 新增超线文件能被识别。
- 新增依赖环能被识别。
- 修改认知状态能选择实际受影响的消费者测试。
- 修改模型协议能触发相应契约检查。
- 改名不能消除旧复杂度或有效例外。
- 未映射的新文件不能被静默忽略。
- CI 失败、跳过和未执行不会被显示为全部通过。

定期以完整回归核对增量选测的漏检情况。

## FM-08：交付形式与完成标准

提供一套可重复执行的只读采集与检查入口，输出：

1. **文件地图**：机器可读，支持增量更新与消费者查询。
2. **代码规模报告**：分类总量、领域分布和版本差分。
3. **复杂度报告**：C901、规模热点、趋势及例外。
4. **依赖影响报告**：直接／反向消费者和质量门映射。
5. **CI 执行报告**：实际运行项目、耗时、失败、跳过、未覆盖范围。
6. **基线记录**：准确 commit/tree、工具版本、规则版本和统计口径。

报告应能由固定版本源码重新生成。

不得为报告和仪表盘创建大量重复维护的人工文件；数据源保持单一，其他展示从同一结果生成。

**完成判据：**

- 能准确回答小夏有多少自维护生产代码、各领域多少行、复杂度热点在哪里。
- 能回答修改一个文件将影响哪些实际业务和消费者。
- 能根据影响范围快速选择必要测试。
- 能阻断真实违规与回归。
- 增量结果与定期完整回归不存在未解释的重大漏检。
- 不以测试数量增加、代码拆分数量增加或报告数量增加宣称工程质量改善。
