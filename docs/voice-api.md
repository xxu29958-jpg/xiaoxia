# 桌宠与其他客户端复用

统一入口 `http://127.0.0.1:6190`。读取本机 `.runtime/voice/service.key`，请求携带 `Authorization: Bearer <key>`。若配置了其他 `voice_state`，密钥位于该目录。密钥只在本机保存。

| 接口 | 输入 | 输出 |
|---|---|---|
| `GET /health` | 无 | 引擎、参考音频摘要、最近请求耗时、忙碌状态 |
| `POST /speech` | JSON `{"text":"嗯，我听着呢。"}` | PCM WAV；响应头含生成耗时和音频时长 |
| `POST /v1/audio/transcriptions` | multipart 字段 `file` | JSON `{"text":"识别结果"}` |
| `POST /cover` | 以下 JSON | 完整演唱 WAV，含伴奏时混回原伴奏 |

说话可传 `{"text":"真来啊？那我等你。","emotion":"happy","emotion_strength":0.08}`。
`emotion` 支持 `neutral`（默认，沿用参考语气）、`happy`、`angry`、`sad`、`afraid`、`disgusted`、`melancholic`、`surprised`、`calm`；强度范围 0–1，默认 0.08。这是轻度情绪控制的待试听起点，不代表自然度已通过验收。音色参考始终保持 QQ 那条 4 秒录音。

IndexTTS-2 按强度混合情绪；CosyVoice3 使用轻度自然语言指令，`emotion_strength: 0` 关闭额外情绪，大于零均使用同一轻度指令，不提供连续强度插值。它缓存同一参考的音频特征，不增加情绪分类模型调用。`6191/health` 和合成响应头报告实际说话后端；`6190/health` 标识统一网关。

2026-11-03 按用户要求，本机候选切换为 `Fish S2 + Seed-VC`。S2 生成说话方式，随后复用常驻 Seed-VC 转回同一个 QQ 四秒参考音色。`emotion` 继续由现有一轮聊天生成；`neutral` 不添加标签，其他语气使用 S2 原生指令，`emotion_strength: 0` 关闭额外指令。全流程仍由 `/speech` 返回一份 WAV，QQ／微信客户端无需修改。候选切换不代表真人感或完整听说唱 Goal 已通过验收。

这条候选使用独立 Fish 环境。源码固定在 `fishaudio/fish-speech@0f8a12e8a651062fdee9c33a894bdccd3a8513f1`，S2 权重固定在 `fishaudio/s2-pro@1de9996b6be38b745688de084d87a5633f714e4e`。`setup.ps1 -WithFish` 额外准备 Python 3.11.15 的 `.venvs/fish`、固定源码和完整权重；已有配置选择 `fish` 时自动准备它。新配置的源码默认位于 `.runtime/sources/fish_speech`，权重在 `models/fish-s2`。安装完成后使用 `xiaoxia.py voice-engine fish` 明确切换，安装额外引擎本身不切换现用声音。

`vendor/sources.json` 固定源码压缩包 SHA-256；已有不同内容的源码拒绝覆盖，外部源码路径只验证。`requirements/fish.in`、`fish-overrides.txt` 和 `fish.provenance.json` 记录依赖来源及生成命令；`fish.lock` 保存全部 Windows 依赖版本和分发哈希。安装使用已完成依赖解析的完整锁文件，不再解析浮动依赖。上游显式覆盖了 `descript-audiotools` 的旧 protobuf 限制，因此 `uv pip check` 仍会报告这一项已登记冲突，不能把它描述成无冲突环境。

模型清单位于 `models-manifests/fish.json`，包含许可证、配置、分词器、解码器和两份权重分片，下载后按 SHA-256 核验。离线源码可用 `python -m tools.installation.fish --archive <固定版本ZIP>` 准备。已有安装可继续设置 `fish_repo`、`fish_models`、`python_fish` 指向实际路径；这些路径和当前声音参考不会由本次迁移自动改写。

切换命令会重启语音网关以应用 GPU 使用方式。Fish 与常驻音色转换共享显存；其解码器中始终被逐窗口掩码覆盖的固定掩码不再保留。启动整组语音服务时，先完成演唱模型的预热，再载入 S2。演唱请求期间先把 S2 移到 CPU，完成后下一次说话自动移回 GPU。

CosyVoice3 缓存 QQ 参考及各情绪所需特征后，释放只负责读取参考录音的两个编码器。2026-11-03 同进程对照中，提交内存由 12.155 降至 10.157 GiB；两组随机种子、四类短长文案的 8 组 WAV 与原版逐字节一致。短句合成均值 1.254 → 1.186 秒，存在运行次序影响，不能据此承诺整轮聊天提速。启用后实测九种情绪、关闭额外情绪、唱后说话识别和显存释放后恢复均正常。更换参考仍需重启服务。

聊天中的语气由现有一次回复结合上下文给出，不增加情绪分类模型调用；字段不进入用户文字或长期对话记录。响应头 `X-Voice-Emotion` 返回引擎实际采用的语气；旧服务没有该响应头时不能据此认定情绪控制已生效。

Codex 聊天请求同时携带回复对象的 JSON Schema，避免模型把正文与情绪字段分开输出、导致内部字段被念出来。格式随当前请求传递，普通请求和其他提供商的现有行为保持不变；流式调用和工具查询后的最终回复也沿用该格式。不增加纠错模型调用，话题和表情字段仍可省略。

日常语音沿用短接话，解释问题仍保留原来的长度上限；没有话题更新或新表情反应时，不再生成空的内部字段。“语音回我”和“用语音回复我”都可触发，“不用语音回我”保持文字回复。Codex OAuth 聊天连接跨轮复用，客户端在提供商关闭时释放。

已提交的完整语音经识别后，开始新一轮回复时直接交给模型，不再额外等待文字连发的收集窗口。文字输入、明确要求等一下的语音和话还没说完的语音沿用原有等待。回复上下文同时带入本轮确实来自语音的事实。

2026-11-03 在现用 WebChat 共用链路中，用同一组八轮连续情境对照：完整语音回复平均 9.192 → 6.510 秒，模型调用平均 4.919 → 3.178 秒，合成平均 3.166 → 2.196 秒；回复平均 24 → 15.8 字。模型与 QQ 参考音色均未更换，合成缩短主要伴随回复变短。这是该组本机测试结果，不能代替手机端送达和真人感验收。另做的六次请求对照中，连接握手由六次减为一次。

随后用另一组六段相同录音作为真实 Record 附件，分别走修改前后的识别、接话和语音回复链路：六段输入的识别文字均匹配原文（忽略标点），五段返回语音，一段按要求只打字。开始处理回复的平均等待 0.867 → 0.156 秒；全六轮平均 7.442 → 6.390 秒，其中五轮语音回复平均 8.160 → 6.942 秒。后者还受模型耗时和回复长度影响，不能全归因于去掉等待。这次未停语音引擎，未改变音色或情绪强度；测试范围是本机 WebChat，不包含新一轮手机或麦克风验收。

Index 说话请求采用 `torch.inference_mode()`，省去推理时不需要的梯度跟踪。停机对照后，三种文案、三组随机种子的九组交错配对，合成平均 2.198 → 2.069 秒，九组均更快且各组 WAV 字节一致。线程数维持 6；音色、情绪强度和采样参数未改。这是本机合成阶段约 5.9% 的改善，不是整轮聊天提速或自然度验收结果。

两个大权重文件使用内存映射加载；QQ 参考的说话人和情绪特征预热后，释放已完成工作的参考编码器，后续直接复用特征。本机新进程对照中，完成十段短句、长句和情绪切换后，进程提交内存 14.860 → 11.212 GiB，工作集快照 5.945 → 4.611 GiB，十组 WAV 均与原版逐字节一致；长句包含两段约 18～19 秒的音频。正常启动及让出显存后重新说话均已验证，固定参考的更换仍通过重启生效。

```json
{
  "source_path": "C:/Music/演唱音源.mp3",
  "acapella": false,
  "pitch": 0,
  "start_seconds": 0,
  "duration_seconds": null
}
```

`duration_seconds: null` 处理完整剩余录音；正数选择片段。`acapella: true` 表示已有人声独唱，跳过伴奏分离。`pitch` 是明确要求的人声半音位移，默认为 0，伴奏保持原音高。可用 `source_url` 代替 `source_path`，下载失败会返回 `422 source_unavailable`，客户端可让用户提供音源。

响应头：`X-Voice-Engine`、`X-Generation-Seconds`、`X-Audio-Seconds`；演唱还提供 `X-Result-Path`。演唱目录保留源人声、伴奏、转换人声、成品和实际耗时，便于继续调音。

演唱的中间 WAV 和单独人声采用浮点格式，保留分离、转换后超过满幅的峰值；最后混音再调整播放增益，接口返回的仍是 PCM16 WAV。这样避免中间文件先削平高音、之后降低音量也无法恢复的问题。2026-11-03 的同一段 30 秒昆曲实测中，源人声峰值为 1.430，旧整数保存将其截到 1.0；修复后保留原峰值，最终成品峰值 0.980、无削波。同次验证还通过 441.504 秒整曲的 26 段转换、8.115 秒简谱演唱，以及唱完后的 CosyVoice3 说话与识别。整曲采用已分离人声，处理 63.680 秒；这些结果不代表听感或手机端的新验收。

请求是同步生成：桌宠应异步等待，收到 WAV 后播放。Cosy／Index 路径的长曲请求不占用日常说话请求锁，演唱会在分段之间给日常说话让出 GPU。当前 Fish 候选在 16 GB 显卡上让说话与演唱依次使用 GPU，长曲生成期间的语音回复需要等待；文字聊天仍可继续。

说话与演唱引擎的 `/health` 都报告实际加载参考文件的 `reference_sha256`。换参考后重启语音服务，不能只修改显示名称。
